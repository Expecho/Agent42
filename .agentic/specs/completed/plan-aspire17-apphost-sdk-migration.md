# Plan: Aspire 17 AppHost SDK migration (ASPIRE012 + AddProject deprecation)

## Overview

Aspire 17.0.0 (released 2026-11-17, https://aspire.dev/whats-new/aspire-17/) marks `Aspire.AppHost.Sdk`
obsolete (ASPIRE012) and deprecates `AddProject<TProject>` in favour of `AddDotnetProject` from the new
`Aspire.Hosting.Dotnet` package. Agent42 already runs Aspire 17.0.0 packages (`Directory.Packages.props`), so
the AppHost builds today with a warning and a deprecated registration. Move off both now, while the change is
small (one csproj, one call site), and confirm the other 17.0 breaking changes do not touch us.

## Affected areas (verified against the tree at eeefba0)

- `src/Agent42.AppHost/Agent42.AppHost.csproj` — line 1 `Sdk="Aspire.AppHost.Sdk/17.0.0"`, a `ProjectReference`
  to `Agent42.Backend`, a `MessagePack` PackageReference.
- `src/Agent42.AppHost/AppHost.cs` — `builder.AddProject<Projects.Agent42_Backend>("backend")` is the only
  `Projects.*` use. `Projects.*` is generated by the SDK from `ProjectReference`s, so it disappears with them.
- `src/Agent42.AppHost/aspire.config.json` (`appHost.path`) — likely unchanged, verify `aspire run` still finds it.
- `Directory.Packages.props` — central versions; `Aspire.Hosting.Dotnet` (+ `Aspire.Hosting.AppHost` if not
  transitive) must be added here.
- `.github/workflows/pr-checks.yml` and `deploy.yml` — build `Agent42.slnx`, which includes the AppHost; verify
  nothing relies on the AppHost's `ProjectReference` to build Backend first.

## Context & constraints

- **Findings that need NO code change (checked, with evidence):**
  - No `AddParameter` / `ParameterResource` anywhere in `src/Agent42.AppHost` → the "required parameters reject
    empty values" breaking change does not apply.
  - No `configureClientOptions` / `CosmosClientOptions` in `src` or `tools`; the only Cosmos client call is
    `builder.AddAzureCosmosClient("cosmos")` in `src/Agent42.Backend/Storage/AzureStorageRegistration.cs:19`, with
    no options callback → the Cosmos signature change does not apply.
  - `OpenTelemetry.Extensions.Hosting` is already 1.21.0 (`Directory.Packages.props:97`), past the 1.18 OTLP
    64 MiB default change. `ServiceDefaults/Extensions.cs` sets no `MaxRequestSizeBytes`. Only a batch over
    64 MiB would be dropped, which is not a realistic span/log batch here → no change; record it, do not add
    config speculatively.
  - Not used at all: RabbitMQ, MongoDB, Azure AI packages, Docker Swarm, Let's Encrypt, AKS.
- **Unknowns the executor must resolve first (Step 1):** whether `Aspire.Hosting.Dotnet` brings
  `Aspire.Hosting.AppHost` transitively; whether `Aspire.Hosting.Orleans`/`Azure.*` still resolve without the SDK;
  whether `AddDotnetProject` wants a relative `.csproj` path (page example:
  `builder.AddDotnetProject("webapplication1", "../WebApplication1/WebApplication1.csproj")`).
- **Without the SDK, nothing builds Backend for the AppHost.** The page says to replace resource
  `ProjectReference`s; `AddDotnetProject` runs the project by path. Check that `aspire run` /
  `dotnet run --project src/Agent42.AppHost` builds Backend on demand. If it does not, keep a
  `ProjectReference` with `ReferenceOutputAssembly="false"` (build ordering only) and say so in the PR.
- **The `MessagePack` PackageReference** in the AppHost csproj exists for a reason the code does not state
  (likely a transitive pin). Do not remove it in this change; git blame it and leave it.
- **Rule 4 (CLAUDE.md):** resolve versions with `dotnet add package`, never write a version from memory. The
  page says 17.0.0 packages exist; still let the tooling resolve.
- **Fallback if the migration fights back:** set `SuppressAspireAppHostSdkObsoleteWarning=true` and leave
  `AddProject` (deprecated, not removed). Record as a follow-up rather than blocking the MR.
- No ADR governs the AppHost SDK or `AddProject`. Grep `.agentic/decisions/` for `AppHost` hits only
  incidental mentions (0001, 0007, 0012, 0019, 0039, 0059, 0062, 0068, 0069, 0076); none contradicts this
  change. No `/decide` step needed unless the fallback is taken, in which case the suppression is a tiny
  decision worth a gotcha, not an ADR. No gotchas entry covers Aspire hosting.
- `docs/setup/local.md` and `CLAUDE.md` Commands table describe `dotnet run --project src/Agent42.AppHost`;
  the command must stay valid.

## Steps

1. **Spike the shape** (not parallelizable; everything depends on it). On a `chore/aspire17-apphost-sdk` branch
   off main: `dotnet add src/Agent42.AppHost package Aspire.Hosting.Dotnet`. Run `aspire update --migrate`
   only if it helps; otherwise edit by hand. Note the resolved version it pins into `Directory.Packages.props`.
   Verify: `dotnet build src/Agent42.AppHost` is the next step's check, so just record findings for the
   unknowns above.
2. **Migrate the csproj.** `Sdk="Microsoft.NET.Sdk"`; add `Aspire.Hosting.AppHost` (and `Aspire.Hosting.Dotnet`)
   PackageReferences without versions (CPM); drop the `Agent42.Backend` `ProjectReference` (or demote per the
   constraint above); keep `UserSecretsId`, `MessagePack`, the three existing Aspire hosting references.
   Verify: `dotnet build src/Agent42.AppHost` — zero ASPIRE012 warning, zero errors — AND
   `dotnet build Agent42.slnx`. If a `ProjectReference` to Backend was kept, the slnx build is the one that
   catches Web-SDK exe-to-exe / scoped-css problems (`Directory.Build.props` already works around one such
   case for DevHost -> Backend). Also confirm the SDK's implicit pieces (dashboard/DCP orchestration, launch
   metadata) still arrive: the AppHost must still start in Step 4; do not treat a clean build as proof.
3. **Swap the call site.** In `AppHost.cs`, replace `AddProject<Projects.Agent42_Backend>("backend")` with
   `AddDotnetProject("backend", "../Agent42.Backend/Agent42.Backend.csproj")`; keep the whole `.WithReference`
   / `.WithEnvironment` / `.WaitFor` chain and every comment intact. Check `DotnetProjectResource` accepts the
   same chain (typed builders may need a tweak, per the page). Verify: `dotnet build Agent42.slnx`.
4. **Run the AppHost against the emulator** (needs Docker). `dotnet run --project src/Agent42.AppHost` (or
   `aspire start`): confirm cosmos + storage emulators, searxng and backend all reach Running, the backend UI
   loads, and a chat round-trips (canned/any provider) so Orleans + Cosmos state is exercised, and that
   `/dashboard` is reachable for `local-dev` (the owner override in `AppHost.cs`). Check the new default
   container images (Azurite 3.35.0→3.37.0) did not break blob upload. This step is a manual check by design
   and needs the user's Docker; if Docker is unavailable, say so and report SKIPPED, never claim it passed.
5. **Docs sweep.** `/sync-docs`: if `docs/setup/local.md`, `README.md` (lines ~268, 293), `CLAUDE.md` or any doc names the SDK or `Projects.*`, fix it. If
   nothing changes, say so. Note in the PR body the checked-and-unaffected list from Context.
6. **Run the gates.** `dotnet build Agent42.slnx`, `dotnet test Agent42.slnx`,
   `dotnet format Agent42.slnx --verify-no-changes`.

Steps are sequential; none are worth fan-out.

## Divergence from the plan (recorded at execution, 2026-11-21)

- **`Aspire.Hosting.AppHost` is a required direct PackageReference**, not transitive. NuGet does not import a
  transitive package's `build/` targets, so without it the `apphostprojectpath` assembly metadata is never
  emitted and `AddDotnetProject` resolves its relative path against the process working directory. Added to
  the csproj and `Directory.Packages.props` (17.0.0, resolved by `dotnet add package`).
- **`<Using>` items replace the SDK's implicit usings** (`Aspire.Hosting`, `Aspire.Hosting.ApplicationModel`);
  `AppHost.cs` needed no `using` lines.
- **No `ProjectReference` to Backend was kept.** `AddDotnetProject` builds the project itself through a
  `__dotnet-project-build` resource, so the plan's `ReferenceOutputAssembly="false"` fallback was not needed.
- **`aspire.config.json` gained `sdk.version: 17.0.0`**, written by `aspire update --yes`.
- **New local prerequisite: Aspire CLI 17+.** Without the SDK, DCP and the dashboard come from the global CLI
  bundle (`ASPIRE_DCP_PATH` pointed at the CLI's own `dcp`). Documented in `README.md` and `docs/setup/local.md`.
- **Step 4 needed a machine fix, unrelated to the migration.** DCP 0.27.3 refused to start (`restricted file
  policy ... file owner is not the administrators group` on `~\.dcp\state.elevated`), which `main` hit
  identically. Moving `~\.dcp` aside fixed it. Once the AppHost ran, all resources reached Running; `/`,
  `/dashboard` (`local-dev` owner) and `/api/config-health` answered 200; an attachment upload reached Azurite
  and a chat POST wrote the conversation to Cosmos (it then failed on "no model", expected with no provider).
- **Pre-existing bug found, not fixed here:** the Backend crashes at startup in any local run because
  `appsettings.json` ships `AzureOpenAI:TenantId` as `""` and `Azure.Identity` 1.21.0 (bumped in #261) rejects an
  empty tenant. Reproduced with the Backend alone. Step 4 was verified with `AzureOpenAI__TenantId` set to a
  dummy GUID in the environment. Follow-up: a separate `fix/*` branch.
- **Gate result:** the 5 failing tests are all live tests (`LiveCopilot*`, `LiveModelChatTests`) that need real
  credentials (HTTP 401 on the Azure key); everything else passed (3898).
